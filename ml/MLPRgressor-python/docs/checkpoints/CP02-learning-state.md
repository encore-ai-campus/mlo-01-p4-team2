# CP02 학습과 모델 버전 및 영구 상태

## 1. 진입과 종료

계획 작성은 CP01 계획 검토 PASS 후에 한다.
구현은 전체 문서 최종 검토 PASS와 CP01 구현 게이트 완료 후에 시작한다.
범위는 MLP 학습과 로컬 저장이다. 광고 API 호출과 실행 재시도는 후속 단계다.

종료 순서는 코드 검토 PASS → 저장 계약 검증 → 해당 테스트와 CP01 회귀 테스트다.

## 2. 산출물과 초기 모델

- `model.py`: MLPRegressor 최초·추가 학습, 예측 형·유한성 검사.
- `state.py`: 환경 확인, 실행 잠금, 원자 저장, 모델 버전과 진행 상태.
- `tests/test_learning.py`, `tests/test_state.py`.

최초 학습 모델은 없다. 정상 행이 있을 때 새 모델을 만든다.
입력14 → 은닉32 → 은닉16 → 출력3 구조를 초기값으로 쓴다.
solver=adam, random_state=42로 시작한다. GPU나 새 학습 프레임워크는 추가하지 않는다.
TRAIN_EPOCHS만큼 같은 어제 정상 행을 순회한다. 기본100회는 검증된 최적값이 아니다.
이후에는 저장한 모델의 partial_fit을 사용한다.
입력은0~1이고 첫 버전에서는 별도 표준화를 추가하지 않는다.

예측 결과는 반드시 `(정상행수,3)` 모양이며 전부 유한해야 한다.
잘못된 예측은 모델 버전과 API 결과를 저장하기 전에 중단한다.
원본0행·미확정·정상0행이면 모델 생성·학습·추론을 하지 않는다.

## 3. 저장 구조와 환경 확인

```text
STATE_DIR/
  run.lock
  state.json
  models/v000001.joblib
  models/v000002.joblib
  runs/2026-11-11_completed.json
```

새 학습 성공마다 모델과 학습 이력을 같은 버전 파일에 보관한다.
각 버전은 덮어쓰지 않는다. 자동 삭제도 하지 않는다.
API 재전송, 보류, 같은 날짜 중복 실행으로 모델 버전을 만들지 않는다.
광고 프로필의 version과 ML 모델 버전은 서로 다른 값이다.

모델 파일에는 모델 객체와 아래 학습 정보를 함께 담는다.

- 모델 버전·직전 모델 버전·학습 대상일·Gold snapshot version.
- 입력14 순서·정답 산식 버전·학습 반복 횟수·학습 행 통계.
- Python major.minor와 sklearn·numpy·joblib 버전.
- 비밀값 없는 환경 식별 정보와 저장 UTC 시각.

state.json은 현재 모델 버전과 학습 완료일을 가리킨다.
전송 완료일, 고정된 미전송 결과, 묶음 진행 위치, 마지막 실행 결과도 보관한다.
state.json에도 Python major.minor·sklearn·numpy·joblib 버전과 입력·정답 정의를 저장한다.
이 정보는 joblib 밖에 있으므로 모델을 역직렬화하기 전에 비교할 수 있다.

실행은 state.json의 환경 식별과 입력·정답 정의를 먼저 검사한다.
모델이 있으면 저장된 학습 환경도 먼저 확인한다. 다르면 joblib을 읽지 않고 중단한다.
API 주소·Gold root·별도 S3 endpoint가 바뀌면 새 STATE_DIR가 필요하다.
키만 바뀌면 기존 상태를 사용할 수 있다. 키와 비밀 storage_options는 저장하지 않는다.

모델은 이 프로그램이 만든 신뢰 가능한 파일만 읽는다.
경로를 임의로 지정한 외부 모델을 불러오는 기능은 만들지 않는다.
모델 버전 이름을 검사해 경로 이탈을 막는다.

## 4. 원자 저장과 상태 전이

한 상태 디렉터리에 대한 파일 잠금을 사용한다. Linux·macOS가 실행 대상이다.
다른 서버의 다른 로컬 상태 디렉터리까지 잠그지는 못한다.

학습 결과를 게시하는 순서는 다음과 같다.

1. 기존 정상 버전을 메모리로 읽어 학습한다. 기존 파일을 수정하지 않는다.
2. 예측 전체를 검증하고 고정된 전송 후보를 준비한다.
3. 새 버전 파일을 임시 파일로 쓰고 fsync 후 새 이름으로 게시한다. models/ 디렉터리도 fsync한다.
4. state.json에 새 모델·런타임·학습 완료일·전송 후보·offset0을 함께 원자 저장한다. 교체 후 상태 디렉터리도 fsync한다.
5. CP04는 이 상태 저장이 끝난 뒤에만 광고 API 쓰기를 시작한다.

새 버전 파일 생성은 기존 버전을 덮지 않는 방식으로 한다.
버전 번호는 기존 파일을 고려해 할당한다. 중단 때문에 번호가 건너뛸 수 있다.
버전 파일 게시 후 state.json 저장 전에 중단되면 참조되지 않는 파일이 남을 수 있다.
이 파일은 자동으로 최신 모델로 선택하지 않는다. state.json이 가리키는 버전만 사용한다.
다중 파일의 원자성을 주장하지 않는다. 원자적으로 바꾸는 state.json이 사용 여부를 결정한다.

전송 진행 상태는 성공한 묶음마다 저장한다.
모델 버전 파일을 매 묶음마다 다시 쓰지 않는다.
성공 응답 후 상태 저장 전에 중단돼도 같은 요청을 재전송할 수 있어야 한다.

| 상황 | 모델·학습 이력 | 전송 처리 |
|---|---|---|
| 학습 또는 게시 전 실패 | 기존 버전 유지 | 쓰기 없음 |
| 새 버전·후보 원자 저장 성공 | 새 학습 버전 유지 | 이후부터 쓰기 가능 |
| 같은 대상일 전송 실패 | 재학습 없음 | 고정된 후보부터 재개 |
| 같은 대상일 모두 완료 | 새 버전 생성 없음 | 완료로 종료 |
| 날짜가 지난 미전송 후보 | 이미 학습한 사실 유지 | 후보는 대체 기록으로 보관하고 자동 게시 금지 |
| 공급 보류·정상0행 | 모델·학습 완료일 유지 | CP04의 빈 감사·보류 처리 |

학습 완료와 전송 완료를 다른 필드로 둔다.
과거 전환율 정정은 완료한 날짜의 자동 재학습을 일으키지 않는다.

## 5. 기록과 복구 범위

각 모델은 학습 이력을 포함하므로 이전 버전의 근거를 찾을 수 있다.
완료·보류·대체 기록은 runs/에 날짜와 상태로 남긴다.
원시 예외·키·비밀 환경값은 기록하지 않는다.

현재 버전이 손상되거나 환경이 맞지 않으면 중단한다.
자동으로 옛 모델을 선택하거나 옛 전송 결과를 게시하지 않는다.
이번 범위는 버전 보관과 재개다. 임의 버전 롤백 명령은 추가하지 않는다.
운영자가 모델 파일만 바꿔 학습 이력과 진행 상태를 어긋나게 만들지 않도록 실행 문서에 적는다.

## 6. 검증과 테스트

코드 검토 PASS 이후 순서대로 확인한다.

1. 저장 필드·파일 권한·상대 경로·입력/정답 버전·비밀값 제외를 정적으로 확인한다.
2. 실제 MLP 최초 학습과 다른 날짜 추가 학습을 수행한다.
3. 모델 버전이 늘고 이전 모델 파일의 해시가 그대로인지 확인한다.
4. 저장한 모델·학습 이력을 읽어 입력14와 출력3을 확인한다.
5. 모델 파일 게시·디렉터리 fsync·state.json 교체 사이의 실패를 주입한다. state.json 교체 전 실패면 이전 포인터를 유지해야 한다.
   교체 뒤 실패면 완전한 새 포인터가 남을 수 있다. 어느 경우에도 포인터가 미완성 모델을 가리키면 안 된다.
6. 환경 불일치는 joblib 로딩·원격 호출 전에 실패해야 한다. 키 교체는 허용돼야 한다.
7. 같은 상태 잠금 경쟁을 시험한다. 두 학습이 동시에 진행되면 실패다.
8. 원본0행·전부미확정·필터 후0행에서 모델 생성·버전·학습 완료일 변경이 없는지 확인한다.

초기 모델 정확도나 실제 광고 성과 향상을 이 단계의 통과 기준으로 삼지 않는다.
