# CP03 광고 Internal API 클라이언트

## 1. 진입과 종료

계획 작성은 CP02 계획 PASS 후에 한다.
구현은 전체 문서 최종 검토와 CP02 구현 게이트 완료 후에 한다.
이 단계는 C8의 읽기·쓰기 클라이언트를 구현한다. 자체 API 서버와 DB 드라이버는 없다.
종료 순서는 코드 검토 PASS → C8 계약 대조 → 모의 HTTP 테스트와 기존 회귀 테스트다.

## 2. 산출물과 원본

- `ads.py`: 요청, 커서 읽기, 묶음 쓰기, 응답 검사와 오류 분류.
- `tests/test_ads.py`: 네트워크를 사용하지 않는 가짜 HTTP 응답 시험.
- 정본: `../../contracts/internal.openapi.yaml`. 요약: `../../contracts/internal.md`.

설정 검사는 CP01의 공통 설정을 사용한다. HTTP 구현은 표준 라이브러리로 시작한다.
알 수 없는 응답 필드는 무시한다. 필요한 응답 필드와 우리가 쓰는 값은 검사한다.

## 3. 요청과 읽기

- 기본 주소 뒤에 `/ad-groups`, `/profiles/weights`를 붙인다.
- `X-Internal-Key`와 JSON Content-Type을 사용한다. 매체 키는 사용하지 않는다.
- HTTP redirect를 따라가지 않는다. 다른 주소에 키가 전달되면 안 된다.
- CP04가 준 만료 시각을 요청 직전에 확인한다. 만료됐으면 네트워크 호출 없이 보류한다.

목록은 `GET /ad-groups?limit=200`으로 읽는다. state=unclassified를 붙이지 않는다.
첫 요청은 after 없이 보낸다. 이후 next_after를 사용하며 null이면 끝난다.
정규화한 광고ID·cursor를 검사한다. 광고 중복과 cursor 반복은 계약 오류다.
한 페이지의 items는 배열이고 최대200개여야 한다.
profile은 null일 수 있다. 있다면 아래 필드를 검사한다.

- ad_group_id: 해당 광고와 같은 UUID. 대문자와 소문자는 정규화해 비교한다.
- version: bool이 아닌1이상 정수.
- category: null 또는0~255 정수. bool은 거절한다.
- weight_mlo/aio/skn: 각각 실제 정수0~100, 합계100이하.
- changed_at: 실제로 존재하는 UTC Z 시각. 소수 초는1~6자리다.

광고 이름·소재·URL·이미지는 가중치 모델의 입력으로 쓰지 않는다.
GET의 범위가 제한됨을 유지한다. 읽기에서 빠진 광고를 임의로 추가하지 않는다.

## 4. 묶음 쓰기

전송 항목에는 네 필드만 허용한다.

```json
{"ad_group_id":"0197a5c0-7e2a-7c3d-9f10-2b3c4d5e6f70","weight_mlo":60,"weight_aio":30,"weight_skn":10}
```

본문은 `{"items":[...]}`다. 같은 광고를 중복으로 보내지 않는다.
200개와 직렬화한 UTF-8 본문64KiB 제한을 모두 검사한다.
각 가중치는 실제 Python int여야 한다. bool과60.0은 거절한다.
합계100이하를 확인한다. source, 모델버전, 기준version을 추가하지 않는다.
보낼 것이 없으면 CP04가 빈 묶음을 한 번 요청한다.

200 응답은 보낸 항목 수·순서·ID가 맞아야 한다.
항목별 result는 created/changed/unchanged 중 하나여야 한다.
profile은 읽기와 같은 검사를 통과하고, 저장된 가중치가 보낸 값과 같아야 한다.
category는 가중치 쓰기로 변경하지 않는다. DB와 outbox 처리는 광고 서버 책임이다.

## 5. 응답 제한과 진단

모든 200 응답의 X-Request-ID를 UUID로 검사해 호출 기록에 남긴다.
오류 응답에서도 유효한 X-Request-ID를 얻을 수 있으면 보관한다.
응답 ID 오류, 필요한 본문 필드 오류, 잘못된 JSON은 계약 실패다.
NaN·Infinity 같은 비표준 JSON 숫자도 거절한다.

응답은 한 번에4MiB까지만 읽는 보호 한도를 둔다.
이 값은 C8이 보장한 응답 상한이 아니다. 초과 시 원인을 구분해 중단한다.
실제 페이지가 이를 넘으면 읽기 페이지 축소 또는 한도 조정을 별도로 검토한다.
무제한 읽기나 같은 큰 응답의 자동 반복은 하지 않는다.

로그에는 고정 오류 코드·상태 번호·유효한 요청ID·허용된 오류 위치만 남긴다.
임의 오류 메시지·URL·헤더·응답 본문 전체를 출력하지 않는다.
400은 알려진 code와 `/items/...` 등 계약 위치만 제한적으로 기록한다.
원격 문자열을 그대로 예외 메시지에 붙이지 않는다.

## 6. 오류와 재시도 경계

이 클라이언트의 요청 함수는 호출당 한 번만 전송한다.
재시도 횟수와 대기는 CP04의 한 제어 지점에서만 결정한다.

| 상황 | 분류와 전달 |
|---|---|
| 503 + 유효 Retry-After | 일시적 실패, 서버가 요구한 초와 요청ID 전달 |
| 연결·시간초과·응답 본문 중단 | 일시적 통신 실패 |
| 400/401/403/413/415 | 자동 반복하지 않는 실패 |
| 잘못된 요청ID·JSON·본문 계약 | 자동 반복하지 않는 실패 |
| 그 밖의 계약 밖 상태 | 자동 반복하지 않는 실패 |
| 만료한 대상일 | 자동 전송하지 않는 보류 |

Retry-After는 C8대로0이상 정수 초를 받는다. 잘못되면 계약 오류다.
HTTPException의 IncompleteRead·RemoteDisconnected도 통신 실패에 포함한다.
본문이 끊긴 쓰기는 이미 저장됐을 수 있다. CP04가 저장한 같은 묶음으로 재시도한다.
새 예측이나 새 학습을 이 클라이언트에서 시작하지 않는다.

동일 값 쓰기 재시도는 단일 가중치 작성자 전제에서 사용한다.
다른 작성자가 중간에 새 값을 쓰면 옛 재시도가 덮을 수 있다. C8에는 원자적 기준version 검사가 없다.

## 7. 검증과 테스트

코드 검토 PASS 이후 다음 순서로 진행한다.

1. 정본의 경로·보안 헤더·필드·형·합계·크기·오류를 정적으로 대조한다.
2. 모르는 응답 필드 무시, 필수 필드 검사와 실제 int 직렬화를 확인한다.
3. 커서 끝·대문자UUID·광고 중복·cursor 반복을 테스트한다.
4. 200개·64KiB·빈 묶음과 잘못된 합계·bool·float·추가 요청 필드를 테스트한다.
5. 응답 항목 수·순서·ID·가중치·UTC·요청ID 오류를 테스트한다.
6. 503/Retry-After와 400/401/403의 서로 다른 분류를 확인한다.
7. IncompleteRead와 연결 실패가 재시도 가능한 오류가 되는지 확인한다.
8. redirect와 만료 요청이 외부 호출을 만들지 않는지 확인한다.
9. 응답 크기 한도와 비밀값이 포함된 오류 본문을 시험한다. 비밀값이 로그에 없어야 한다.

실제 API 호출은 하지 않는다. 실행 재시도와 여러 묶음 복구는 CP04에서 통합 시험한다.
