# Laya 분류 파트 API 호출 계약

상태: v3.1 서브 에이전트 검토 통과. 필수 지적 0건. 작성일: 2026-11-12.
원본: 광고 서버 C8 v1.0.0 확정 계약과 최신 대화의 결정.
[저장소 기준 계약](../../../docs/legacy/ads-server/contracts/internal.openapi.yaml)을 `docs/contracts/`에 복사했다.
요약 문서와 OpenAPI가 다르면 OpenAPI를 따른다.

이 문서는 이전 v2의 자체 HTTP 서버·직접 DB 저장 설계를 대체한다.
문서 두 개의 재검토를 통과한 뒤 구현한다.

## 1. 역할과 범위

우리는 광고 분류 파트다.
광고 서버에서 자료를 받아 요약·분류하고 카테고리 API에 결과를 보낸다.
DB 갱신, version, changed_at, 감사 기록, Outbox는 광고 서버가 담당한다.
가중치 쓰기 API는 호출하지 않는다.
현재는 로컬 모의 응답으로만 통신한다. `192.168.0.204` 접속과 테스트는 금지한다.

| 방향 | 방법과 경로 | 목적 |
|---|---|---|
| 분류 파트 → 광고 서버 | GET `/api/internal/v1/ad-groups?state=unclassified&limit=200` | 매일 미분류 광고 조회 |
| 분류 파트 → 광고 서버 | GET `/api/internal/v1/ad-groups?limit=200` | 모델 변경 등에 따른 별도 전수 재분류 |
| 분류 파트 → 광고 서버 | POST `/api/internal/v1/profiles/categories` | 분류 결과 저장 요청 |
| 분류 파트 → OpenAI | POST `/v1/responses` | URL 실제 읽기와 요약 |

자체 실행 API, 상태 조회 API, 완료 알림 API는 만들지 않는다.
이전 완료 알림과 그 재시도 기능도 제거한다.
실행 결과와 진행 기록은 JSON 파일에 남긴다.

## 2. 주소와 인증

| 설정 | 뜻 |
|---|---|
| ADS_API_BASE_URL | 광고 서버 기본 주소. `/api/internal/v1`까지 포함 |
| ADS_INTERNAL_KEY | 환경변수에서 읽어 X-Internal-Key 헤더에 넣을 값 |
| OPENAI_API_KEY | OpenAI 호출용 별도 키. 현재 빈 값 유지 |

실제 내부키가 저장돼 있다고 가정한다. 값을 출력하거나 기록하지 않는다.
광고 서버 요청 모두에 X-Internal-Key를 보낸다. OpenAI에는 이 키를 보내지 않는다.
현재 시험은 숫자 루프백 주소 127.0.0.1 또는 ::1의 모의 광고 서버만 허용한다.
환경변수 HTTP_PROXY·HTTPS_PROXY·ALL_PROXY를 사용하지 않는다.
호스트 이름이나 DNS 조회를 거쳐 주소 제한을 우회하지 않는다.
리다이렉트를 따라 실서버로 이동하지 않는다.
SSH 포트 27을 HTTP API 포트로 사용하지 않는다.

## 3. 매일 분류하는 순서

1. state=unclassified로 첫 페이지를 요청한다. 첫 요청에는 after를 넣지 않는다.
2. 받은 광고마다 소재 하나의 title과 redirect_url을 사용한다.
3. 요약·분류에 실패한 광고는 실패 목록에 기록한다. 저장 항목에 넣지 않는다.
4. 정상 분류 결과를 최대 200개씩 카테고리 API에 보낸다.
5. 200 응답의 항목별 result를 확인하고 성공 건수를 올린다.
6. next_after가 있으면 같은 state와 limit에 after를 넣어 다음 페이지를 받는다.
7. next_after=null까지 반복한다.

이 API가 제공하는 대상은 모든 DB 행과 같지 않다.
종료·관리자 중단·비활성 광고주 등의 광고는 조회 대상에서 빠진다.
우리는 서버가 반환한 범위만 처리한다. 별도 DB 조회로 범위를 늘리지 않는다.
한 번 훑는 동안 생성된 일부 광고가 빠질 수 있다. 다음 정기 실행에서 다시 조회한다.

서버는 제목과 이동 주소가 있는 소재를 하나 이상 반환한다. 이미지 유무는 조회 기준이 아니다.
분류에서는 사용자 결정에 따라 광고 하나당 소재 하나만 사용한다.
creatives가 비었거나 여러 개면 임의로 고르지 않고 해당 광고를 실패 처리한다.
profile=null은 허용한다. 광고 서버가 첫 저장에서 판 1을 만든다.
image_url은 응답에 있어도 이번 분류에서는 사용하지 않는다.

## 4. 카테고리 쓰기

요청 본문은 다음 모양이다.

```json
{
  "items": [
    {"ad_group_id": "11111111-1111-4111-8111-111111111111", "category": 12},
    {"ad_group_id": "22222222-2222-4222-8222-222222222222", "category": 0}
  ]
}
```

한 항목은 소재가 아니라 광고 하나의 결과다.
같은 광고 ID를 한 요청에 두 번 넣지 않는다.
category는 JSON 정수 0~255다. null·bool·실수·문자열은 보내지 않는다.
Content-Type은 application/json이며 직렬화한 본문은 64 KiB 이하다.
source, version, changed_at, 가중치를 요청 본문에 추가하지 않는다.

### 4.1 정상 응답

광고 서버는 보낸 순서대로 items를 반환한다.
ID·개수·result·반영된 profile을 대조하고 모르는 추가 필드는 무시한다.

| result | 우리 쪽 집계 | 서버 동작 |
|---|---|---|
| created | 성공 | 최초 profile과 판 1 생성 |
| changed | 성공 | 값 변경과 version 증가 |
| unchanged | 성공 | 같은 값 유지. version과 changed_at 유지 |

성공 집계는 분류 완료 시점이 아니라 저장 API의 200 결과를 확인한 뒤 반영한다.
재시도 뒤 받은 result는 마지막으로 확인한 응답 기준이다.
첫 요청의 응답이 유실됐다면 최초 저장이 created였는지 다시 추측하지 않는다.

### 4.2 항목 오류 400

그 요청의 앞선 시도에 결과 불명이 없었다면, 400은 해당 묶음의 미저장을 뜻한다.
앞선 시도가 503·통신 실패였다면 먼저 5절의 결과 불명 규칙을 적용한다.
errors[].pointer의 `/items/<번호>`를 현재 요청 배열의 광고 ID에 연결한다.
같은 광고의 오류가 여러 개여도 실패 건수는 한 번만 올린다.
식별된 오류 광고를 실패 목록에 넣고 제외한다.
나머지 광고만 새 묶음으로 재전송한다. 분류를 다시 수행하지 않는다.
새 응답에서 다른 오류 광고가 드러나면 같은 규칙을 적용한다.
매번 최소 한 항목이 줄어들어야 하며 같은 400을 무한 반복하지 않는다.

모든 오류 위치가 요청 안의 항목으로 대응할 때만 개별 분리를 수행한다.
전체 오류나 범위 밖 위치가 섞인 400은 묶음 전체를 실패 처리한다.
이때 임의의 광고 하나를 원인으로 지정하지 않는다.
해당 묶음을 그대로 자동 재전송하지 않는다.

### 4.3 빈 실행

조회가 끝났고 보낼 정상 결과가 한 건도 없으면 `{"items": []}`를 한 번 보낸다.
미분류가 없는 날에도 이 요청을 보낸다.
이는 실행 감사 기록을 위한 요청이다. 성공 광고를 한 건으로 세지 않는다.
이 요청의 일시 오류에도 아래의 전송 재시도 규칙을 적용한다.

## 5. 광고 서버 요청 재시도

최초 호출을 포함해 요청마다 최대 3회다.
이 규칙은 삭제한 완료 알림의 재시도와 별개다.

| 조건 | 처리 |
|---|---|
| 503 | Retry-After의 초 값을 기다린 뒤 같은 요청 재전송 |
| 타임아웃·연결 실패 | 첫 실패 후 10초, 다음 실패 후 30초 뒤 같은 요청 재전송 |
| 400 | 오류 항목을 분리하는 규칙 적용. 원래 요청을 그대로 반복하지 않음 |
| 401·403 | 자동 재시도 중단. 전체 실행을 인증 오류로 종료 |
| 413·415 | 같은 요청을 자동 재시도하지 않고 요청 오류로 기록 |

503은 저장되지 않았다는 보장이 아니다.
같은 요청의 어떤 시도라도 503·통신 실패가 있었다면 저장 결과 불명 문맥을 유지한다.
이후 400·401·403·다른 오류가 와도 앞선 시도의 저장을 취소한 것으로 해석하지 않는다.
최종 200을 확인하기 전에는 해당 ID를 확정 실패로 세거나 pending에서 제거하지 않는다.
이 경우 오류 항목 분리도 하지 않고 전체 미확인 ID를 보존한 채 실행을 종료한다.
3회 뒤에도 쓰기 결과를 확인하지 못하면 WRITE_OUTCOME_UNKNOWN을 기록한다.
해당 광고를 확정 성공이나 확정 실패에 더하지 않는다.
counts_final=false로 전체 실행을 종료하고 미확인 광고 ID를 남긴다.
쓰기 결과 JSON이 잘못됐거나 요청과 대응하지 않아도 저장 결과를 단정하지 않는다.
X-Request-ID를 읽어 요청 오류 기록에 남긴다. 키나 전체 응답 본문은 남기지 않는다.

## 6. 동시 변경 정책

기준 version과 소재 수정 시각은 쓰기 요청에 넣지 않는다.
현재 계약의 마지막 쓰기 우선 규칙을 따른다.
분류 담당은 이 모듈 하나라는 사용자 결정을 따른다.
동일 값의 재전송은 unchanged가 될 수 있다.
이 정책을 오래된 광고 내용의 저장 방지 보장으로 표현하지 않는다.

## 7. 결과 JSON

결과와 진행 기록은 `var/jobs/{job_id}.json`에 둔다.
명령줄의 결과 JSON에도 최상위 source=laya를 넣는다.
광고 서버 쓰기 요청에 source를 넣는 것은 아니다.

```json
{
  "source": "laya",
  "job_id": "33333333-3333-4333-8333-333333333333",
  "status": "completed_with_failures",
  "total": 100,
  "processed": 100,
  "succeeded": 98,
  "failed": 2,
  "counts_final": true,
  "failures": [
    {"ad_group_id": "11111111-1111-4111-8111-111111111111", "stage": "summary", "reason": "URL_READ_FAILED"},
    {"ad_group_id": "22222222-2222-4222-8222-222222222222", "stage": "write", "reason": "AD_SERVER_REJECTED"}
  ]
}
```

total은 실제 읽은 광고 수다. 실행 시작 시 서버 전체 건수를 안다고 가정하지 않는다.
processed=succeeded+failed이며 최종 정상 순회에서는 total과 같다.
전송 중 광고 ID는 pending_write_ids로 기록한다.
응답 유실이나 중단 시 이 ID들의 DB 상태를 JSON만으로 확정하지 않는다.
재시작하면 이전 running을 interrupted로 기록하며 자동 재개하지 않는다.
자체 실행 API 제거로 별도 접수 대기열과 콜백 상태는 만들지 않는다.

## 8. 현재 시험 범위

실제 광고 서버 접속·SSH·운영 DB·Outbox 쓰기는 수행하지 않는다.
모의 광고 서버로 조회·페이지·검증 오류·재시도·저장 응답을 시험한다.
OpenAI 키는 빈 값이며 실제 유료 호출을 수행하지 않는다.
현재 시험은 OpenAI 키의 존재와 무관하게 명시적으로 모의 요약기를 선택한다.
이 모의 요약 경로는 외부 요청을 수행하지 않으며 OpenAI 키를 요구하지 않는다.
실제 OpenAI 요약 경로만 빈 키를 사전 검사한다. 키가 비면 조회 전에 종료한다.
모의 OpenAI 응답과 실제 로컬 Laya 추론을 구분해 보고한다.
