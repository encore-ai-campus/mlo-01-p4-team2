# 강의 중 캠퍼스 이용 일시정지

이벤트맵 화면 위쪽의 **관리자 운영 제어**는 활성 상태인 Django `is_staff` 계정에만 보입니다. 일반 계정이 API를 직접 호출해도 상태를 바꿀 수 없습니다.

1. 관리자 운영 제어를 열고 안내 문구를 입력합니다.
2. **강의 중 이용 일시정지**를 누르면 캠퍼스 이용이 중단됩니다.
3. 정지 안내창의 **캠퍼스 이용 재개**를 누르면 다시 이용할 수 있습니다.
4. 재개 후에는 조작키를 놓았다가 다시 누릅니다. 정지 전 입력이 자동으로 이어지지 않습니다.

## 적용 범위

- 서버 입력 처리에서 이동, 달리기, 점프, 공격, 방어, 빠른 이동, 부스 상호작용을 차단합니다.
- HTTP API에서 학습, 게시판, 개인 메시지, 콘텐츠 열기, 이벤트 미션, 광고 신규 요청 등을 차단합니다. 전체 채팅 WebSocket에도 같은 정지 검사를 적용합니다.
- 로그인, 계정 설정, 로그아웃, 정지 상태 확인과 관리자 재개는 계속 이용할 수 있습니다.
- 마지막 위치, 학습 세션, 작성 중인 화면은 유지합니다. 현재 학습 기능에는 별도의 제한 시간 타이머가 없습니다. 이벤트 종료 날짜 같은 실제 시각의 운영 규칙은 바뀌지 않습니다.
- 페이지를 켜둔 이용자는 정지 상태 확인 시 비활동 로그아웃을 방지합니다. 기존 로그인 최대 수명 및 다른 기기의 로그인에 의한 종료 정책은 유지합니다.
- 이미 다른 탭에서 열린 외부 게임·영상 자체를 강제로 중단시키지는 않습니다. 새로 열기 요청은 차단합니다.
- 이미 접수된 DB 트랜잭션은 완료될 수 있습니다. DB 트랜잭션을 강제로 멈추거나 되돌리지 않습니다.

## 분리 배포

이동 PC와 서비스 PC에 같은 버전과 마이그레이션을 적용하고, 두 역할이 같은 서비스 DB를 사용해야 합니다. 서로 다른 Redis를 사용해도 정지 상태는 같은 DB 행으로 공유합니다. 실행 중인 서버가 상태를 최대 약 1초 간격으로 다시 읽고, 이동 소켓의 대기 틱을 포함해 대체로 1.5초 이내에 반영합니다. 네트워크·DB 지연은 별도입니다.

`platform_server/backend/`에서 `python manage.py migrate`를 실행한 뒤 각 역할의 서버를 다시 시작합니다. 정지 상태는 서버를 재시작해도 유지됩니다. 최초 설치 시 기본 상태는 이용 가능이며, 설치만으로 강제 정지하지 않습니다.

## 기록과 비용

`campus_control_freezestate`의 1번 행에 현재 상태와 revision을 저장합니다. `campus_control_freezechange`에는 상태 변경당 관리자·정지 여부·문구·시각을 한 건씩 기록합니다. Kafka 토픽은 추가하지 않습니다. 프로세스별 공유 캐시가 있어 이용자 또는 프레임마다 DB를 조회하지 않습니다. 클라이언트는 기존 이동 소켓 알림과 15초 간격 상태 확인을 함께 사용합니다.

정지 중에도 heartbeat·상태 확인·세션 유지 트래픽은 발생합니다. 기존 이동·공격 처리와 콘텐츠 이용은 줄어듭니다. 오래된 입력 패킷은 revision 검사로 재개 후에도 거절합니다.
