# 이동 EC2와 채팅·HTTP EC2 분리

이 폴더는 배포 예시다. 운영에는 적용하지 않았다.

```text
브라우저 → 기존 HTTPS 입구
          ├─ /ws/movement/ → 이동 EC2 :8000 → 9101·9102·9103·9104
          └─ /ws/chat/ 및 API → 서비스 EC2 :8000 → 9201·9202·9203·9204
```

| 실행 위치 | 프로세스 | 담당 |
|---|---|---|
| 이동 EC2 | `config.movement_asgi:application` 4개 | 위치·충돌·점프·찌르기·상태 전달 |
| 서비스 EC2 | `config.service_asgi:application` 4개 | 채팅·로그인·게시판·댓글·쪽지·학습 API |

두 역할은 같은 소스와 DB 모델을 사용한다. 실행 진입점과 프로세스가 다르다.
이동 서버에는 일반 HTTP API와 채팅 경로를 열지 않는다.
서비스 서버에는 이동 경로를 열지 않는다.
TLS 암호화는 기존 HTTPS 입구에서 처리한다.

## 실행 예시

이동 EC2에는 `playdata-movement@.service`와 `nginx-movement.conf`를 사용한다.
이동 프로세스는 `9101`, `9102`, `9103`, `9104`에서 각각 실행한다.
서비스 EC2에는 `playdata-service@.service`와 `nginx-service.conf`를 사용한다.
서비스 프로세스도 `9201`, `9202`, `9203`, `9204`에서 각각 실행한다.
서비스 프로세스 1개와 1 CPU 제한은 집중 요청 시험에서 병목이 됐다.
서비스 EC2의 CPU를 쓰도록 여러 프로세스를 실행한다.

서비스 systemd 예시는 `MYSQL_POOL_SIZE=8`로 MySQL 연결 풀을 사용한다.
이동 systemd 예시는 `MYSQL_POOL_SIZE=0`으로 기존 연결 방식을 유지한다.
두 값은 공통 `.env`를 읽은 뒤 실행 명령에서 적용한다.
SQLite에는 연결 풀을 적용하지 않는다.

서비스의 HTTP와 채팅 DB 작업은 같은 프로세스별 풀을 사용한다.
서비스 4개이면 풀의 연결 상한은 `4 × 8 = 32`개다.
채팅의 기존 DB 작업 스레드가 유지하는 연결도 이 상한에 포함된다.
이동 프로세스와 별도 작업 프로세스의 DB 연결은 별도로 계산한다.

HTTP 요청은 `CONN_MAX_AGE=0`을 유지하며, 요청 종료 시 연결을 풀에 돌려준다.
풀 대기는 최대 2초이며, 초과하면 Django `OperationalError`로 전달한다.
연결 확인과 반납 시 rollback은 SQLAlchemy의 기존 동작을 사용한다.
실패한 SQL을 자동으로 다시 실행하지 않는다.

systemd 예시의 `/home/ubuntu/backend`는 실제 설치 경로에 맞춰야 한다.
각 EC2의 Nginx는 같은 파일을 쓰지 않는다.
입구의 `/ws/movement/`만 이동 EC2의 내부 주소로 보낸다.
입구의 `/ws/chat/`와 기존 API 경로는 서비스 EC2로 보낸다.
브라우저가 보는 도메인은 하나로 유지한다.

프런트 Django 중계를 사용할 때는 다음 주소를 설정한다.

```dotenv
BACKEND_URL=http://<서비스_EC2_내부주소>:8000
MOVEMENT_BACKEND_URL=http://<이동_EC2_내부주소>:8000
```

## 두 EC2에서 같아야 하는 설정

- `DJANGO_SECRET_KEY`: 이동 서버가 서명한 아바타 토큰을 채팅 서버가 검사한다.
- DB 주소와 DB 이름: 로그인·사용자·게시판·채팅 기록을 함께 사용한다.
- `CAMPUS_REDIS_URL`: 이동 프로세스 간 상태와 로그인 종료 알림을 전달한다.
- `DJANGO_ALLOWED_HOSTS`: 실제 HTTPS 도메인과 필요한 내부 Host를 허용한다.

채팅 메시지의 아바타 연결에는 Redis 이동 좌표를 조회하지 않는다.
공통 로그인 만료 처리에서는 마지막 위치를 Redis에서 읽어 저장할 수 있다.
아바타 ID와 층은 이동 서버가 서명한 `chatToken`으로 전달한다.
토큰에는 세션 쿠키 원문을 넣지 않는다.
채팅 서버는 채팅을 보낼 때 로그인 상태와 사용자 이름을 다시 확인한다.

Redis와 DB의 주소를 `127.0.0.1`로 두 EC2에 각각 복사하면 서로 다른 저장소가 된다.
실제 공유 저장소의 내부 주소를 사용해야 한다.
EC2 내부 포트는 HTTPS 입구와 필요한 서버의 보안 그룹에만 허용한다.

DB 스키마 변경과 기존 `campus_jobs`는 중복 실행하지 않는다.
이동·채팅 프로세스를 띄우는 것만으로 별도 작업 프로세스가 실행되지는 않는다.

## 배포 경계

클라이언트도 두 WebSocket 경로를 사용하도록 바뀐다.
기존 클라이언트가 `/ws/campus/`로 채팅까지 보내는 배포와는 함께 사용할 수 없다.
새 경로·서버·프런트 정적 파일을 한 배포 단위로 준비해야 한다.

HTTPS 인증서·보안 그룹·실제 EC2 주소는 이 예시에 포함하지 않았다.
Nginx 문법 검사와 로컬 시험 결과는 상위 성능 보고서를 참고한다.
