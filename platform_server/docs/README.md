## 1. 광고판 근처에서만 광고 요청 — 먼저 할 작업

### 목표 동작

- 광고판에서 멀리 있거나 다른 층이면 광고를 요청하지 않는다.
- 광고판이 곧 화면에 들어올 범위에 접근하면 광고와 이미지를 미리 받는다.
- 광고가 화면에 보이는 동안 서버의 10초 회차에 맞춰 갱신한다.
- 화면 밖으로 충분히 멀어지면 갱신을 중단한다.
- 재진입할 때는 기존 광고의 유효 상태를 확인하고 필요한 요청만 보낸다.

광고판 좌표, 카메라 위치·줌, 캔버스 크기를 사용해 브라우저에서 요청 여부를 판단한다. 좌표를 광고 서버에 전송하는 작업은 아니다. 사전 로딩 영역은 실제 표시 가능한 캔버스 영역의 바깥 256 CSS px, 이탈 기준은 384 CSS px로 정했다. 접근 시 한 번 미리 받고 화면 밖에서 머무는 동안에는 회차 갱신을 하지 않는다. 화면과 일부라도 겹치면 회차 갱신을 허용한다. 대기 응답과 일시적 오류는 근처에 있는 동안 재시도하며, 이탈하면 진행 중 응답·이미지의 표시를 무효화한다. 모달이 열렸거나 탭이 숨겨진 동안에도 새 요청을 중단한다.

| `src/frontend/dist/campus-ads.js` | 접근 시 사전 요청, 표시 중 갱신, 이탈 시 중단 및 재진입 처리 |

## 2. 사용자별 광고 요청

현재 옥상 광고는 shared 슬롯과 `roof:<10초 회차>` 키를 사용하므로 같은 회차의 광고를 공유한다. 이를 individual 슬롯과 사용자별 배치로 바꾼다.

- 로그인 정보에서 읽은 내부 사용자 UUID를 로컬 `owner_id`로 사용한다.
- 배치 키는 `roof:<owner_id>:<10초 회차>` 형태로 사용자와 회차를 구분한다.
- 동일 사용자의 동일 회차 요청은 재사용하고, 다른 사용자의 발급은 분리한다.
- 광고 서버에는 현재 방식의 `subject_id`를 전달한다. 지금 단계에서는 HMAC 생성 방식을 유지한다.
- 향후 기존 사용자 UUID를 직접 보내는 전환은 별도 단계로 진행한다. API 필드명 변경 여부는 광고 서버 계약과 함께 확정하며, 이번 단계에서 `user_uuid` 필드로 바꾸지 않는다.
- 사용자별 요청이어도 광고 서버의 선택 결과에 따라 같은 광고가 나올 수 있다. 관심사 추천 로직은 이번 범위에 포함하지 않는다.

주요 수정 대상은 `src/backend/ad_bridge/placements.py`, `game/placements.py`와 관련 테스트다. 사용자 식별 및 발급 기록 연결도 함께 확인한다.

### 완료 기준

- [ ] 실제 연결할 옥상 individual 슬롯 ID와 매체 키 연결을 확인한다.
- [ ] 동일 사용자·회차의 중복 요청과 동시 요청을 재사용한다.
- [ ] 사용자 간 배치와 클릭 권한이 섞이지 않는다.
- [ ] 발급 당시 owner_id·subject_id·decision_id 연결을 유지한다.
- [ ] 기존 포털 광고와 과거 발급 기록의 조회·재전송에 영향을 주지 않는다.

## 3. 클릭 저장 → 광고 서버 확인 → 이스터에그

현재 `report_click()`은 사용자·토큰·발급 광고를 검증한 후 `record_ad_click()`을 호출하고 광고 서버로 303 이동한다. 광고 서버의 실제 클릭 저장 여부를 확인하는 단계와 별도 클릭 이력 테이블은 없다.

### 변경할 흐름

```text
사용자 광고 클릭
  → 우리 서버에서 로그인 사용자·서명 토큰·발급 광고 검증
  → 우리 DB에 클릭 접수를 확인 대기 상태로 저장
  → 기존 광고 서버 클릭 주소로 303 이동
  → 서버 작업자가 광고 서버의 클릭 저장 여부 조회
  → 실제 클릭이 확인되면 로컬 기록을 확인 완료 상태로 저장
  → 같은 DB 트랜잭션에서 기존 record_ad_click() 호출
  → 커밋 후 기존 업적 알림 전달
```

### 로컬 기록과 처리

- 내부 사용자 UUID, decision_id, 발급 당시 subject_id, 접수 시각, 확인 상태를 보관한다.
- 광고 서버가 확인해 준 클릭 식별자·클릭 시각과 확인 시각을 저장한다. 정확한 필드는 API 계약에 맞춰 정한다.
- 동일 사용자·decision의 중복 접수는 기존 기록을 재사용한다.
- 일시적인 통신 오류나 아직 조회되지 않는 클릭은 정책에 따라 재확인한다. 재시도 간격·종료 조건은 계약 확정 후 정한다.
- 광고 서버 저장이 확인되지 않은 상태에서는 업적을 지급하지 않는다.
- 확인 완료 기록과 업적 처리가 중복 실행되거나 일부만 반영되지 않도록 트랜잭션과 동시 실행 처리를 검증한다.
- 클릭 이력은 업적 획득 여부와 관계없이 저장한다.

주요 수정 대상은 `src/backend/ad_bridge/models.py`, `migrations/`, `game/views.py`, 광고 API 클라이언트, 확인 작업자 및 관련 테스트다. 기존 노출 재전송 코드의 동작을 바꾸지 않도록 클릭 확인 처리를 설계한다.

### 광고 서버와 확정할 계약

- [ ] decision_id와 발급 당시 subject_id로 실제 저장된 클릭을 확인할 수 있는 API
- [ ] 매체 인증 및 해당 매체 기록만 조회할 수 있는 접근 범위
- [ ] 광고 서버가 직접 관측한 클릭인지 구분할 응답 정보
- [ ] 클릭 식별자·시각·미확인 응답·오류·재시도 규칙

현재의 `POST /api/ads/decisions/<decision_id>/result/`는 노출 상태 조회다. 이 API가 클릭 확인을 지원한다고 가정하지 않는다. 클릭 확인 계약이 준비되기 전에는 이 단계를 완료로 표시하지 않는다.

```text
src/

  backend/
    ad_bridge/             광고 API 연동·저장·재전송·테스트

  SOURCE_MAP.md            src 파일과 기존 실행 경로 대응
```

`src/`는 필요한 파일만 모은 작업용 복사본이다. 게임은 여전히 루트의 `frontend/`, `backend/`를 사용한다. 작업 중에는 src를 수정하고, 통합할 때 실제 변경 파일만 기존 경로에 반영한다. Git은 src 경로를 기존 경로에 자동 대응시키지 않는다.

현재 1단계에서 수정한 isometric.js, campus-ads.js와 두 테스트 파일은 기존 실행 경로에도 반영되어 있다.

기준 커밋 이후 event에서 바뀐 내용이 있으면 변경을 합쳐야 한다. 복사본 전체로 원본을 덮어쓰지 않는다. 자세한 대응 경로와 통합 원칙은 [SOURCE_MAP.md](SOURCE_MAP.md)를 참고한다.

## 검증

프론트 테스트는 작업 폴더 루트에서 실행한다.

```powershell
node --test src/frontend/tests/campus-ads.test.cjs src/frontend/tests/ad-visibility.test.cjs src/frontend/tests/ad-display.test.cjs src/frontend/tests/isometric.test.cjs
```

백엔드 복사본은 전체 Django 프로젝트 의존성을 포함하지 않는다. 변경 파일을 기존 실행 경로에 반영한 뒤 프로젝트 설정으로 백엔드 테스트를 수행한다. 클릭 테이블 추가 시 PostgreSQL에서 마이그레이션, 유일성 제약, 트랜잭션 및 동시 처리도 검증한다. 실제 환경의 DB 설정은 통합 전에 확인한다.

실제 게임에서는 접근·이탈·층 이동·카메라 확대·축소에 따른 요청 횟수와 노출 보고를 확인한다. 클릭 단계는 광고 서버 연동 환경에서 저장 확인부터 업적 반영까지 검증한다.

현재 코드의 URL과 호출 흐름은 [ROUTING.md](ROUTING.md)를 참고한다.
