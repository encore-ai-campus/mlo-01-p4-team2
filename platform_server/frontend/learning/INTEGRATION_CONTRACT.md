# Python / CS / SQL 학습 연결 계약

기준일: 2026-11-04. 화면은 `frontend/learning/`, 업무·DB·이벤트는 `backend/learning/`과 `backend/eventing/`에 있음.

## 기존 데이터와 제출 식별

문제·세션·답안의 기존 정수 PK를 보존함. 문제와 보기에는 UUIDv4를 추가하고 답안별 `attempt_uuid` 및 사용자별 요청 식별자인 `submission_request_uuid`를 저장함. HTTP 답안 제출에는 UUIDv4 요청 키가 필요함. 같은 요청의 재시도는 저장한 응답을 반환하고, 같은 키로 다른 답안을 보내면 거부함.

## 포인트 저장

`PointWallet`은 기존 플랫폼 사용자 UUID에 연결됨. `PointLedger`는 지급 원장 UUID·답안 시도 UUID·지급 포인트·지급 후 잔액·지급 시각을 저장하며 한 시도당 한 번만 생성됨. 답안·성적·지갑·원장·응답 스냅샷을 같은 DB 트랜잭션에 저장함. 동일 사용자의 동시 제출도 잔액 갱신을 직렬화함.

객관식과 빈칸 모두 정답이면 기본 초급 20P·중급 50P·고급 80P를 적립함. API 포인트 상태는 `connected`이며 실제 지급액과 잔액을 표시함. 잘못된 답안·완료된 문제·요청 재시도에는 중복 지급하지 않음. 기존 답안은 보존하고 소급 지급하지 않음. 향후 팀 운영 모델에 옮길 때도 한 DB 트랜잭션과 원장 유일성을 유지해야 함.

## 기록 저장

현재 event 브랜치는 학습 세션·답안·포인트 원장을 PostgreSQL에 저장한다.
학습 패널 열기는 `content_open_request_log`에 사용자·접속·과목 콘텐츠·학습 구역을 함께 기록한다.
플랫폼 내부의 Outbox와 Kafka 직접 발행은 제거된 상태다. CDC 연결은 별도 작업이다.

## 지도와 교실

18층의 기존 학습 구역을 SQL(`class2`)·CS(`class-cs`)·Python(`class1`) 순서로 세등분한다.
교실 내부는 모두 640×520 크기와 같은 가구·캐릭터·이동 구조를 사용한다.
서버가 출입구 통과를 판정하며, 학습 영역에서 E키를 누르면 해당 과목의 패널을 연다.
CS 칠판은 `11.11 CS CLASS`, 왼쪽은 `CS 객관식`, 오른쪽은 `CS 개념 빈칸 채우기`다.
브라우저는 이동 입력을 보내고 서버가 충돌·교실 출입·학습 영역을 판정한다.
학습 팝업 중에는 이동 입력을 비운다. 지도 원본 변경 후 `node frontend/tools/build-event-map.cjs`로 화면·서버 지도를 함께 생성한다.

개인 교실 좌표는 메인 층의 좌표와 분리된 화면 상태이며 다른 사용자에게 별도 교실 아바타를 방송하지 않음. 퇴장 시 원래 강의실의 복도 쪽으로 돌아옴. 프론트는 지도 확장 마커에 교실·학습 패널과 해시가 붙은 에셋 URL을 삽입함.

## 문제 데이터 범위

레포의 Python·SQL 기존 문제 파일은 총 2,400문항이다. CS 문제 파일은 1,200문항을 추가한다.
과목별 초급·중급·고급과 객관식·빈칸의 여섯 조합마다 200문항을 둔다.
CS는 운영체제·네트워크·컴퓨터 구조·자료구조·알고리즘을 각 조합에 40문항씩 배정한다.
300개 개념을 정의·상황 적용으로 묻고, 각 질문을 객관식과 빈칸 방식으로 제공한다.
기존 문제·세션·답안은 수정하지 않는다. 같은 파일을 다시 적재해도 문제 UUID를 보존한다.

API 경로와 응답 구조는 유지하며 `subject`에 `cs`를 추가한다.
한 세트는 무작위 10문항이고, 문항당 최대 3회 제출한다. 세트 완료 후 7문항 이상 정답이면 통과다.
CS 빈칸은 앞뒤 공백과 영문 대소문자를 무시한다. 내부 공백·다른 용어나 철자는 자동 교정하지 않는다.
질문에는 요구하는 용어의 첫 글자·글자 수를 표시한다. Python·SQL의 기존 채점은 유지한다.
기본 정답 포인트는 초급 20P·중급 50P·고급 80P다.
CS 학습 기록으로 중급 이상 통과 업적을 판정한다.
CS 통과는 메인 미션의 Python 초급 객관식 조건을 대신하지 않는다.

문제 구조 검사는 정답과 보기의 일치·중복·분류별 문항 수를 확인한다. 의미와 난이도는 별도 내용 검수 대상이다.
문제는 직접 작성했으며, 다음 자료를 분야별 참고자료로 사용한다.

- 운영체제: [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/)
- 자료구조·알고리즘: [MIT 6.006 강의 자료](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/pages/lecture-notes/)
- 네트워크: [TCP RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html), [HTTP RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)

학습 업적 및 EE-15 변경 (2026-11-05):
- 과목별 중급·고급 업적은 각 과목의 10문항 세트를 완료하고 7문항 이상 정답이면 달성한다. 객관식과 빈칸 모두 인정한다.
- 세 과목 통과로 지급하던 업적은 제거한다. 기존 업적 UUID를 EE-15 `부서지기 직전`으로 재사용한다.
- 서버 잔량이 정확히 1/10인 사용자가 꾸왕이의 숨겨진 대화에서 새 빼빼로 받기를 확정하면 달성한다. 서버 전체에서 최초 한 명만 받을 수 있으며, 대화 미리보기나 취소만으로는 지급하지 않는다.
- `guide_talk`는 로그인·꾸왕이 위치·잔량·운영 시간을 검증하지만 업적을 지급하지 않는다. `kkuwang_last_bite`의 미리보기·확정 요청에서 서버 인벤토리·운영 시간·전역 선점·계정별 이스터에그 제한을 다시 검증한다. 클라이언트가 보낸 잔량은 판정에 사용하지 않는다.
- `event_story.0013_fragile_pepero_achievement`는 업적 이름을 변경하고 이전 세 과목 통과 달성 기록만 제거한다.
- 기존 학습·답안·포인트 기록은 변경하지 않는다. 업적은 사용자별 `event_progress`에 최초 1회 저장한다.
- 달성 알림은 차례로 표시하고, 재전송은 최초 달성 시각과 알림을 중복 생성하지 않는다.
- EE-15는 서버 전체의 단일 완료 기록으로 관리하며, 계정이 이미 다른 이스터에그를 달성했으면 받을 수 없다.
- EE-15 이미지는 `/static/campus/assets/achievements/fragile-pepero-v1.webp`를 사용한다.

이스터에그 지급 제한 (2026-11-05):
- 이스터에그마다 한 계정만 달성하고, 한 계정은 이스터에그 하나만 달성할 수 있다.
- 모든 지급 경로가 계정 행 → 이스터에그 정의 행 순서로 잠근 뒤 완료 기록을 확인한다. 조건 확인과 저장은 한 트랜잭션에서 수행한다.
- 선점되거나 다른 업적을 가진 계정에는 추가 완료 기록을 만들지 않는다. 기존 완료 시각·접속 UUID는 변경하지 않는다.
- 게임·학습 결과와 메인 미션·스토리 진행은 정상 저장한다. 완료 순위는 해당 이스터에그의 1위로 기록한다.
- `event_story.0014_reset_easter_egg_completions`는 기존 이스터에그 완료 기록만 초기화한다. 메인 미션과 진행 중 기록은 보존한다.
